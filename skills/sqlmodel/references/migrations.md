# SQLModel and Alembic Migrations

Use this reference when changing schema, backfilling data, or preparing
production-safe migrations.

## Setup

Install the toolchain:

```bash
uv add sqlmodel alembic
```

For async projects:

```bash
uv add sqlalchemy[asyncio] asyncpg
alembic init -t async alembic
```

Set `target_metadata = SQLModel.metadata` in `alembic/env.py` and make sure
all models are imported before autogenerate runs.

## Create Migrations

Recommended:

```bash
uv run alembic revision --autogenerate -m "add user table"
uv run alembic upgrade head
```

Create empty migrations for manual work:

```bash
uv run alembic revision -m "custom migration"
```

Autogenerate is a starting point, not a final answer.

## Schema Change Patterns

### Add a Nullable Column

```python
def upgrade() -> None:
    op.add_column("user", sa.Column("phone_number", sa.String(20), nullable=True))


def downgrade() -> None:
    op.drop_column("user", "phone_number")
```

### Add a Required Column Safely

```python
def upgrade() -> None:
    op.add_column("user", sa.Column("role", sa.String(50), nullable=True))
    op.execute("UPDATE user SET role = 'user' WHERE role IS NULL")
    op.alter_column("user", "role", nullable=False)


def downgrade() -> None:
    op.drop_column("user", "role")
```

### Rename a Column

```python
def upgrade() -> None:
    op.alter_column("user", "name", new_column_name="full_name")


def downgrade() -> None:
    op.alter_column("user", "full_name", new_column_name="name")
```

### Add a Foreign Key

```python
def upgrade() -> None:
    op.add_column("post", sa.Column("user_id", sa.Integer(), nullable=True))
    op.create_foreign_key(
        "fk_post_user_id",
        "post",
        "user",
        ["user_id"],
        ["id"],
        ondelete="CASCADE",
    )


def downgrade() -> None:
    op.drop_constraint("fk_post_user_id", "post", type_="foreignkey")
    op.drop_column("post", "user_id")
```

### Add an Index

```python
def upgrade() -> None:
    op.create_index("idx_user_email_username", "user", ["email", "username"], unique=False)


def downgrade() -> None:
    op.drop_index("idx_user_email_username", table_name="user")
```

## Data Migrations

Keep data migrations explicit and reviewable.

```python
def upgrade() -> None:
    op.execute(
        """
        UPDATE user
        SET normalized_email = lower(email)
        WHERE normalized_email IS NULL
        """
    )
```

Rules:

- keep one logical reshape per migration
- document irreversible transforms
- avoid hidden assumptions about row count or data cleanliness
- test data migrations against realistic staging data when possible

## Best Practices

- always review autogenerated migrations
- keep one logical change per migration
- test both upgrade and downgrade when feasible
- use descriptive migration names
- never edit applied migrations in place
- stage complex migrations instead of doing everything in one step

## Rollback Strategy

- keep downgrades honest; if rollback is unsafe or destructive, say so plainly
- test downgrade paths on staging or disposable databases
- use snapshot or backup strategy before risky production changes

## Production Workflow

### Development

1. modify models
2. generate migration
3. review generated SQL and operations
4. test upgrade and downgrade
5. commit the migration

### Staging

1. deploy application code
2. run `uv run alembic upgrade head`
3. verify schema and data integrity
4. test critical app paths

### Production

1. back up the database
2. deploy in a controlled window when required
3. run `uv run alembic upgrade head`
4. monitor logs, metrics, and application behavior
5. verify critical flows

## Zero-Downtime Pattern

For large tables or production-sensitive changes:

1. add the new column as nullable
2. deploy code that can write both old and new fields
3. backfill existing rows
4. make the new column required
5. deploy code that reads the new field
6. drop the old field only after the new path is stable

## Troubleshooting

### Alembic Does Not Detect Model Changes

Make sure `env.py` imports the real model modules before `target_metadata` is
evaluated.

### Migration Fails Midway

Check current state:

```bash
uv run alembic current
```

Then either:

- fix the migration and rerun
- downgrade and retry
- or stamp only when you fully understand the current schema state

### Async Setup Drift

If the app is async but migrations are misconfigured, verify:

- `-t async` was used when initializing Alembic
- the database URL uses the async driver where expected
- the migration environment matches the app's metadata imports

## Checklist

- [ ] metadata imports are correct in `env.py`
- [ ] autogenerated migrations are reviewed
- [ ] destructive steps are intentional
- [ ] data migrations are explicit
- [ ] upgrade path is tested
- [ ] downgrade path is tested or honestly limited
- [ ] production rollout plan matches the blast radius
